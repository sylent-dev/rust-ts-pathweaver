# Technical choices

The libraries, the services and the main designs of Pathweaver, with their reasons and the alternatives rejected. Written with the skeleton on 2026-11-16; completed at step 0 on the same day.

| Subject | Choice | Reasons |
|---|---|---|
| Shape of the application | A website: the core in Rust compiled to WebAssembly, the interface in TypeScript with Svelte 5 and SvelteKit, as in Stepwise | Version 2 is a platform of shared builds: pages with their own address, found by search engines, text to select and to read with a screen reader, which HTML gives and a canvas doesn't. Compared on 2026-11-16, and rejected: the whole application in Rust with egui compiled to WebAssembly (one language, but everything drawn in a canvas: no pages to index, weaker text editing and accessibility, several megabytes to load), fitting a viewer alone but not the platform. The workspace, its checks and the bridge are those of Stepwise, already tried. |
| Bridge | `crates/wasm`, with `tsify` and `serde-wasm-bindgen`: a type of its own for each thing that crosses, its TypeScript type generated from it; under each exported function, a function in plain Rust that `cargo test` calls | As in Stepwise (see its `docs/technical-choices.md`, Bridge): the two sides can't drift, and the crates of the core know nothing of JavaScript. |
| Reading the `.build` files | `serde` and `serde_json` in `crates/build-file`, with `preserve_order`; every object keeps the fields the format doesn't name in `extra` (`#[serde(flatten)]`), and an entry keeps the form it was written in (its id alone or an object, one level or a list) | The format is experimental and will change: a file written by another tool, or by a later version, is written back as it was read. |
| Game data | The passive tree exported by Grinding Gear Games, the rest (gems, uniques, base items, ascendancies) from RePoE; converted at build time by a script of the repository into compact files of the website, one folder per version of the game and per language | The only official export is the tree; RePoE is the export of the files of the game that tool developers use, and every id of the corpus is found in the two. Served by Pathweaver, so that the website doesn't depend on them at run time. Rejected: Path of Building (Lua made for its calculations), poe2db.tw (no API). See [game-data.md](game-data.md). |
| Passive tree | Its data in a crate of the core (graph, positions, which passives apply at a level); drawn by the interface in a canvas (Canvas 2D), with Pathweaver's own shapes | 5,153 nodes: too many for SVG, a few for a canvas. No image of the game on the tree (only the portraits of the ascendancies, elsewhere). |
| Levels and merging | In the core: which entries apply at a level, the markers where the build changes, what changes at a marker, the merging of the builds of a guide and its checks | Rules of the format, tested with `cargo test` on the corpus, and needed by the server of version 2 to check a published build. |
| Share link | The JSON without its spaces, compressed with deflate and written in base64url after the `#` of the address. Where the compression runs (the core in Rust or the `CompressionStream` of the browser) is decided at step 8 | No server and nothing stored; measured on the corpus: 1,926 characters for the median build, 7,348 for the largest. |
| Library | The open builds kept in IndexedDB, through a small module of the interface | No server and no account; IndexedDB holds files of any size, unlike `localStorage`, and the browser may refuse it (private browsing), which the interface handles. |
| Host | Cloudflare: the static website first, then Workers (Rust with `workers-rs`), D1 and R2 for version 2 | The owner's domains and the Workers of Exile Market are already there; no machine to administer; the static files are free, and the free plan stops at its quotas rather than bill. Compared on 2026-11-16, and rejected: a VPS (cheaper than a managed platform, but its updates, firewall and backups by hand), a managed platform such as Fly.io (more expensive, for the same absence of administration). |
| Interface texts | Fluent, in `web/locales/`, as in Stepwise | A language is added without touching the code. |
| Front-end tooling | npm, TypeScript strict, `svelte-check`, ESLint, Prettier, Vitest, as in Stepwise | The configuration every Svelte developer knows, checked in the CI next to Clippy and `cargo test`. |
| The owner's screen | 2,560 × 1,440 pixels (WQHD), noted on 2026-11-16 at step 2 | The mock-up is checked at the smallest width (900 pixels, half of a 1920-pixel screen) and at the owner's, where the page shows wider layouts (the side panel from about 1,400 pixels). |
| Mock-up server | `python3 docs/mockups/serve.py 8796`, from the repository root (`html-mockups` skill) | A port of its own, unused by the owner's other projects (8742, 8753, 8765, 8770, 8781 and 8790 are taken), so that two mock-up servers never take each other's port; no cache, so that a reload never mixes old and new files. |
